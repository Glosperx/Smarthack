# Plan: Scheduled Maintenance Prediction Job

A job that runs `assess_turbine_health` for every turbine at a regular interval and **upserts** the result into `public.turbine_mentenance`, so the map (see `MAP_FEATURE_PLAN_V2.md`) always has a prediction for today.

---

## 1. Goal

- Every N minutes, evaluate all turbines with the ML hook and write one row per turbine per day.
- Re-running is safe: the same turbine and day is **updated**, never duplicated.
- The job is independent of the web server and can be started, stopped, and scheduled on its own.

---

## 2. What the pasted hook does (and what it means for a job)

| Finding | Consequence |
|---|---|
| It **loads the model from disk on every call** | A loop over N turbines reloads the model N times. Add an optional `predictor` argument so the job loads it once (section 6.1) |
| With no `telemetry_records`, it **silently generates synthetic data** (`ScadaSimulator`, fixed seed `42 + asset_id`) | Fine for a demo, dangerous for real use: if a real telemetry fetch comes back empty, the job would write *fake* predictions. The job must treat "no data" as a skip, never pass it through (section 9) |
| The fixed seed makes simulator results **identical on every run** | Idempotent, but a live demo will never change. Use demo scenarios (section 9.2) to get variety |
| The output has more fields than the table has columns (`health_score`, `estimated_days_to_failure`, `anomalous_sensors`, `summary_text`) | Those would be thrown away. An optional migration keeps them (section 5.2) |
| `suspected_subsystem` can be empty for healthy turbines | The column is `NOT NULL`, so we need a placeholder (decision D5) |
| It is a plain synchronous, CPU-bound function | Another reason to keep it out of the FastAPI event loop (decision D2) |

---

## 3. Decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| D1 | Row key | **`(turbine_id, predicted_date)` unique**, with `predicted_date` = the run's local "today" | `predicted_date` alone can't be unique across turbines, so the composite key is the sensible reading of "upsert by `predicted_date`". Matches the UI, which reads `predicted_date = today` |
| D2 | Process model | **Standalone job**: a one-shot CLI that can also loop (`--every`). Not inside FastAPI | CPU-heavy ML would block API requests, a scheduler inside `uvicorn` runs once per worker and per `--reload`, and the write key stays out of the web process |
| D3 | Telemetry | A **seam**: simulator now, real source later behind one function | The real source isn't defined yet |
| D4 | Column mapping | See section 4. `cumulative_fault_probability` copies `fault_probability` **for now** | The hook returns only one probability. Confirm the meaning (section 14) |
| D5 | Empty subsystem | Store the constant `"none"` and have the UI omit the "for …" part for it | No schema change needed. (Alternative: make the column nullable.) |
| D6 | Extra outputs | Add 4 nullable columns and store them (recommended, optional) | The summary and days-to-failure are already computed and are valuable in the drawer |
| D7 | Interval | Default **60 min**, configurable, aligned to the local clock with a 2-minute offset | Keeps the "no prediction yet" gap after midnight to about 2 minutes |
| D8 | Credentials | The job uses a separate **`SUPABASE_SERVICE_KEY`** (secret key). The web API never reads it | Least privilege. Only the job can write |
| D9 | Failures | A failed or no-data turbine is **skipped, never faked**. Others still get written. The run logs a summary | One bad turbine must not stop the other hundreds |
| D10 | Idempotency | Safe to run twice or concurrently. No locking | Same inputs produce the same upserted row |

## 5. Database changes (Supabase SQL editor, ~15 min)

### 5.1 The upsert key (required)

```sql
-- 1) Must return 0 rows. If it doesn't, you have duplicates to clean up first.
select turbine_id, predicted_date, count(*)
from public.turbine_mentenance
group by 1, 2 having count(*) > 1;

-- 2) Only if step 1 returned rows: keep the newest entry per turbine and day.
delete from public.turbine_mentenance a
using public.turbine_mentenance b
where a.turbine_id = b.turbine_id
  and a.predicted_date = b.predicted_date
  and a.entry_id < b.entry_id;

-- 3) The key the job upserts on.
alter table public.turbine_mentenance
  add constraint turbine_mentenance_turbine_date_uniq
  unique (turbine_id, predicted_date);

-- 4) The unique constraint already provides this index, so drop V2's duplicate one.
drop index if exists public.turbine_mentenance_turbine_date_idx;
```

Without step 3, PostgREST rejects the upsert, because `on_conflict` needs a unique constraint or index. This is the constraint `MAP_FEATURE_PLAN_V2.md` §4.2 listed as optional, and it is now required.

### 5.2 Keep the extra outputs (optional, recommended)

```sql
alter table public.turbine_mentenance
  add column if not exists health_score real,
  add column if not exists estimated_days_to_failure real,
  add column if not exists anomalous_sensors text[],
  add column if not exists summary_text text;
```

All nullable, so existing rows and readers keep working.

### 5.3 Write access

The job needs a key that can write. Use the **secret / service-role key**, which bypasses RLS, and keep it only in the job's environment. The read-only policies from V2 §4.3 stay as they are for the web API.

def load_predictor(models_dir: str | Path | None = None) -> TurbineHealthPredictor:
    """
    Load the fault classifier once so callers can reuse it across many assessments.

    resolved_dir = resolve_maintenance_models_dir(models_dir)

### 6.3 Shared "today"

```python
# smarthack/utils/dates.py
from datetime import date, datetime
from zoneinfo import ZoneInfo

def today_in_tz(tz_name: str, now: datetime | None = None) -> date:
    """
    Return the calendar date in the given timezone.

    :param tz_name: IANA timezone name, e.g. "Europe/Bucharest".
    :param now: Optional instant to convert (for tests). Defaults to the current time.

    :returns today: The local date.
    """
    return (now or datetime.now(ZoneInfo(tz_name))).astimezone(ZoneInfo(tz_name)).date()
```

`api/dependencies.get_today()` becomes `return today_in_tz(config.timezone())`. **The API and the job must use the same value**, or the UI looks for a different date than the job writes.

### 6.4 Row schema

```python
# smarthack/schemas/maintenance.py
import math
from dataclasses import dataclass, field
from datetime import date
from pydantic import BaseModel, Field, field_validator

class PredictionRow(BaseModel):
    turbine_id: int
    predicted_date: date
    daily_fault_probability: float = Field(ge=0, le=1)      # also rejects NaN
    cumulative_fault_probability: float = Field(ge=0, le=1)
    status: str
    suspected_subsystem: str
    # optional columns (section 5.2); None is written as NULL
    health_score: float | None = None
    estimated_days_to_failure: float | None = None
    anomalous_sensors: list[str] | None = None              # adjust if the hook returns another shape
    summary_text: str | None = None

    @field_validator("health_score", "estimated_days_to_failure")
    @classmethod
    def _finite_or_none(cls, v: float | None) -> float | None:
        return v if v is None or math.isfinite(v) else None  # JSON can't carry NaN/inf

@dataclass
class RunSummary:
    day: date
    total: int = 0
    written: int = 0
    failed: int = 0
    no_data: int = 0
    duration_s: float = 0.0
    by_status: dict[str, int] = field(default_factory=dict)
```

Passing every result through this model catches NaN, out-of-range probabilities, and numpy scalar types **before** they reach the JSON body.

### 6.5 Supabase client additions

```python
# smarthack/clients/supabase.py (additions)
from itertools import batched

async def fetch_all_turbine_ids(http: httpx.AsyncClient) -> list[int]:
    ids: list[int] = []
    while True:                                           # PostgREST caps responses at 1000 rows
        resp = await http.get(
            _url(TURBINE_TABLE),
            params={"select": "id", "order": "id.asc", "limit": 1000, "offset": len(ids)},
            headers=_headers(),
        )
        resp.raise_for_status()
        page = resp.json()
        ids += [row["id"] for row in page]
        if len(page) < 1000:
            return ids

async def upsert_predictions(http: httpx.AsyncClient, rows: list[dict]) -> None:
    headers = {**_write_headers(), "Prefer": "resolution=merge-duplicates,return=minimal"}
    for chunk in batched(rows, 500):
        resp = await http.post(
            _url(MAINTENANCE_TABLE),
            params={"on_conflict": "turbine_id,predicted_date"},
            headers=headers,
            json=list(chunk),
        )
        resp.raise_for_status()
```

`_write_headers()` is `_headers()` built from `config.supabase_service_key()` instead of the read key. All rows in one request must have the **same keys**, which holds because they come from one model that always dumps every field (`model_dump(mode="json")`, without `exclude_none`).

### 6.6 Service

```python
# smarthack/services/maintenance_service.py
async def run_prediction_cycle(
    http: httpx.AsyncClient,
    *,
    day: date,
    get_telemetry: Callable[[int], Awaitable[list[dict] | None]],   # section 9.1
    turbine_ids: list[int] | None = None,
    dry_run: bool = False,
) -> RunSummary:
    started = time.monotonic()
    summary = RunSummary(day=day)
    ids = turbine_ids or await supabase.fetch_all_turbine_ids(http)
    summary.total = len(ids)
    predictor = load_predictor()                                    # once per cycle
    rows: list[PredictionRow] = []

    for tid in ids:
        try:
            telemetry = await get_telemetry(tid)                    # None = "use the simulator"
            if telemetry is not None and len(telemetry) == 0:
                summary.no_data += 1                                # never fall through to the simulator
                continue
            result = assess_turbine_health(
                asset_id=tid,
                telemetry_records=telemetry,
                scenario=scenario_for(tid),                         # simulator mode only
                predictor=predictor,
            )
            rows.append(_to_row(tid, day, result))
        except Exception:
            logger.exception("Assessment failed for turbine %s", tid)
            summary.failed += 1

    if rows and not dry_run:
        await supabase.upsert_predictions(http, [r.model_dump(mode="json") for r in rows])
    summary.written = 0 if dry_run else len(rows)
    for r in rows:
        summary.by_status[r.status] = summary.by_status.get(r.status, 0) + 1
    summary.duration_s = time.monotonic() - started
    return summary


def _to_row(turbine_id: int, day: date, result: dict) -> PredictionRow:
    p = result["fault_probability"]
    return PredictionRow(
        turbine_id=turbine_id,
        predicted_date=day,
        daily_fault_probability=p,
        cumulative_fault_probability=p,                             # open question 1
        status=result["health_status"],
        suspected_subsystem=result["suspected_subsystem"] or NO_SUBSYSTEM,
        health_score=result["health_score"],
        estimated_days_to_failure=result["estimated_days_to_failure"],
        anomalous_sensors=result["anomalous_sensors"],
        summary_text=result["summary_text"],
    )
```

The loop calls the (synchronous) ML function directly. That is fine in a dedicated job process. If you add concurrent telemetry fetching later, wrap the call in `asyncio.to_thread`.

### 6.7 The job: CLI, loop, schedule

```text
python -m smarthack.jobs.maintenance_job                 # run once, exit
python -m smarthack.jobs.maintenance_job --every 60      # run now, then every 60 min (aligned), until Ctrl+C
python -m smarthack.jobs.maintenance_job --dry-run       # compute and log, write nothing
python -m smarthack.jobs.maintenance_job --turbine-id 3  # only turbine 3 (repeatable)
```

Behavior:
- Builds one `httpx.AsyncClient` with timeouts from `config`.
- Computes `day = today_in_tz(config.timezone())` **at the start of each cycle**, not once at startup, so a long-running loop rolls over at midnight.
- Logs one summary line per cycle: `day, total, written, failed, no_data, by_status, duration`.
- **Once mode:** exits non-zero if nothing was written (so cron, CI, or a systemd timer can alert). **Loop mode:** never exits on failures. It logs and waits for the next cycle, which also repairs transient Supabase errors, since upserts are idempotent.
- The first cycle runs immediately on start, so the demo has data right away.

Clock-aligned scheduling (a pure function, unit-tested):

```python
def seconds_until_next_run(now: datetime, interval_min: int, offset_min: int = 2) -> float:
    """
    Seconds until the next slot of: local midnight + offset, then every interval_min.

    :param now: Timezone-aware local time.
    :param interval_min: Minutes between runs.
    :param offset_min: Minutes after each slot boundary (keeps midnight's first run at 00:02).

    :returns seconds: Delay until the next run.
    """
    midnight = now.replace(hour=0, minute=0, second=0, microsecond=0)
    elapsed_min = (now - midnight).total_seconds() / 60
    k = max(math.floor((elapsed_min - offset_min) / interval_min) + 1, 0)
    next_min = offset_min + k * interval_min
    if next_min >= 24 * 60:                                   # past today's last slot
        next_run = midnight + timedelta(days=1, minutes=offset_min)
    else:
        next_run = midnight + timedelta(minutes=next_min)
    return (next_run - now).total_seconds()
```

With a 60-minute interval, runs land at 00:02, 01:02, … 23:02, so the day's first prediction appears about 2 minutes after midnight.

## 7. Scheduling modes

| Mode | How | Use it for |
|---|---|---|
| **Loop worker** | `make worker` (a third terminal next to `make dev`) | Hackathon, local dev, and the distrobox. Distrobox has no cron or systemd, so the built-in loop is the right fit |
| **One-shot + external scheduler** | `make predict` called by a cron job, systemd timer, GitHub Actions schedule, or Kubernetes CronJob | Production. No scheduler code to babysit, and the platform handles restarts and alerts |
| **Second container** | Same image, different command: `python -m smarthack.jobs.maintenance_job --every 60` | If you deploy the web app as a container. Make sure the model files (`fault_classifier.joblib`, `fault_features.json`) are in the image |

Not recommended: APScheduler inside `create_app()`. It runs once per Uvicorn worker, restarts on every `--reload`, competes with requests for CPU, and needs the write key in the web process.

```make
predict:            # one cycle now
	python -m smarthack.jobs.maintenance_job

worker:             # keep predictions fresh
	python -m smarthack.jobs.maintenance_job --every 60
```

## 8. Failure policy and observability

- A turbine that raises, or returns no data, is counted and skipped. No row is written, so the UI honestly shows "no prediction for today" instead of stale or invented values. (An earlier same-day row, if any, simply stays.)
- Every cycle logs the summary line from 6.7. A cycle with many `failed` turbines is the signal to check the model files or the telemetry source.
- No retry logic. The next cycle retries everything, and the upsert makes that safe. Add retries only if a flaky upstream hurts the demo.
- Supabase write errors (401/403 = wrong key or RLS, 404 = missing table, 400 with "no unique constraint" = step 5.1 not done) are logged with the response body.

## 9. Telemetry

### 9.1 The seam

The service takes a `get_telemetry(turbine_id)` function:
- **Simulator mode** (default for now): returns `None`, so `assess_turbine_health` synthesizes data itself.
- **Real mode** (later): returns that turbine's recent SCADA records as `list[dict]`, from an external API, a localhost service, or files via a new `clients/scada.py` (rank 2). An **empty list means "no data"** and the turbine is skipped.

### 9.2 Demo scenarios

In simulator mode every turbine would be "normal" with identical results on each run. `MAINTENANCE_DEMO_SCENARIOS=3:bearing_overheating,7:gearbox_wear,12:hydraulic_leak` makes those turbines show warnings or critical states, so the map, the sorting (riskiest first), and the status colors can be demonstrated. `scenario_for(turbine_id)` reads this mapping, and it is ignored in real mode.

## 11. Tests

- `to_row` / `PredictionRow`: empty subsystem becomes `"none"`; probabilities outside 0 to 1 and NaN are rejected; non-finite optional floats become `None`.
- `seconds_until_next_run`: 00:00 → 00:02, 00:02:30 → 01:02, 23:30 → next day 00:02, and a non-hourly interval.
- `today_in_tz`: a fixed UTC instant late in the evening yields the next date in `Europe/Bucharest`.
- `upsert_predictions` (`respx`): sends `on_conflict=turbine_id,predicted_date`, the `Prefer: resolution=merge-duplicates` header, the **write** key, and splits 1,200 rows into 3 requests.
- `fetch_all_turbine_ids` (`respx`): follows two pages (a full page of 1000, then a short one).
- `run_prediction_cycle` with `assess_turbine_health` monkeypatched: one raising turbine and one empty-telemetry turbine give `failed=1`, `no_data=1`, and the rest are written; `dry_run=True` calls no write.
- Smoke test (skipped if the model files are absent): one real `assess_turbine_health(asset_id=0, predictor=load_predictor())` maps to a valid `PredictionRow`.

## 14. Gotchas

- **Never let real mode fall into the simulator.** An empty telemetry result must skip the turbine (9.1). Otherwise the job writes fake predictions that look real.
- **The timezone must match** between the API and the job, or the UI reports "no prediction" while rows exist for a different date.
- **PostgREST caps lists at 1000 rows**, so the turbine list is paged, and writes are chunked at 500.
- **JSON can't carry NaN, infinity, or numpy scalars.** That is why every row goes through `PredictionRow` and `model_dump(mode="json")`.
- **Bulk upserts need identical keys in every object.** The fixed row model guarantees it.
- **Sequence gaps:** an upsert uses an `entry_id` value even when it ends up updating, so gaps in `entry_id` are normal.
- **Suspended laptop or stopped distrobox:** the loop pauses with it, and the first cycle after you resume refreshes today's rows.
- **Free-tier Supabase pauses** after inactivity, and the job's writes then fail until the project is woken up.
- **Model files** must exist at runtime (and be copied into any Docker image). Check they aren't gitignored.
- **ML dependencies** (pandas, the classifier's libraries) may live in an optional extra of `pyproject.toml`. Make sure `make install` includes it for the job.

## 15. Open questions

1. **What should `cumulative_fault_probability` mean?** The hook returns a single probability, so it is copied for now. If you want a real cumulative (for example `1 − Π(1 − daily)` over the previous 7 days), that is a change in `_to_row` plus one read of recent rows.
2. **Where will real telemetry come from?** An external SCADA API, a localhost service, files, or a Supabase table? Until then the job runs in simulator mode with demo scenarios.
3. **Is "today's row, refreshed every interval" what you want?** Or should each run also write rows for the next few days (a forecast, one row per future `predicted_date`)? The hook currently produces only one point in time.
4. **Which timezone defines "today"?**
5. **Is 60 minutes the right refresh interval**, or do you want something shorter for the demo (such as 5)?
6. **Is `"none"` acceptable for healthy turbines' subsystem**, or would you rather make the column nullable?
